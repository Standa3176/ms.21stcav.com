## Operator commands for 12.1-05 (nothing here was run against the real portal)
1. `php artisan bitrix:discover-order-fields --json=storage/app/research/order-fields.json`
   - optional `--labels="Cost,Predicted Margin"` (default). Exit 1 on AMBIGUOUS / NOT FOUND / label resolving to UF_CRM_1610623973323.
   - Prints, per label: code, type, required, MANDATORY, and whether the code is in the plugin's mapped-but-blank list. Always lists every "Actual Margin" field (UF_CRM_1610623973323 marked DO-NOT-WRITE), all required deal fields, and categories + stages (incl. category 0). Prints a boxed "D-09 CONFLICT" if Cost/PM is required.
   - JSON: `{cost, predicted_margin, actual_margin_fields, required_fields, categories, stages, generated_at}`.
2. Put the two discovered codes into `database/seeders/Phase12_1/order_parity_map.php` (`pipeline.deal_cost_field`, `pipeline.deal_predicted_margin_field`) via PR.
3. `php artisan bitrix:seed-order-parity` — DRY-RUN, prints diff for pipeline / status_stages / deal_field_mappings, writes nothing (exit 1 if validation fails; diff still printed).
4. `php artisan bitrix:seed-order-parity --apply` — idempotent write inside a DB transaction + `crm.order_parity.seeded` audit record. Optional `--map=<path>` overrides the data file (tests).
   - With the committed file as-is it exits 1: `UNRESOLVED: pipeline.deal_cost_field` and `pipeline.deal_predicted_margin_field` (the only errors).
5. Run `php artisan migrate` first on prod: adds `deal_static_fields` (json), `deal_cost_field`, `deal_predicted_margin_field` (nullable) to `crm_pipeline_settings`.

## Decisions / notes
- **Migration renamed** to `2026_10_27_120000_add_order_parity_columns_to_crm_pipeline_settings.php` (the 100000/100100 timestamps are taken by the supplier-blocks migrations). 12.1-03's planned `2026_10_27_110000` migration would sort BEFORE this one; it must not depend on these columns, or should be renamed to a later timestamp (e.g. 130000).
- Cost / Predicted Margin codes are NOT yet written to the builder at runtime: the builder only uses them as a block-list for static/mapping sources. Writing Cost/PM values is 12.1-03/05 work.
- `status_stages.failed` = null in the map (plugin has failed => NEW, but D-01: a failed order never creates a deal; mapped deals keep their stage). `ywraq-new` / `ywraq-pending` => NEW and `processing` / `on-hold` => '2' are required non-null by validation.
- Stage ids are not auto-verified against Bitrix; the discover command prints category-0 stages so the operator can confirm '2' and 'NEW' exist.
- BitrixClient read methods use `$sdk->core->call(...)` raw (no Money/typed wrapping): `crm.status.list` (ENTITY_ID=DEAL_STAGE) for category 0, `crm.dealcategory.stage.list` otherwise; `crm.deal.productrows.get` for rows. Not exercised against the real SDK (no live calls allowed) — 12.1-05/06 will be the first real run; response-shape handling is defensive (`result`, `result.rows`, bare list).

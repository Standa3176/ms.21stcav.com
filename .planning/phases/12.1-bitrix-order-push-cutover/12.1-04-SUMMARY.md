# Phase 12.1 Plan 04: Shadow hygiene and adopt-legacy hardening Summary

Shadow runs can no longer poison the contact/company map, and legacy-deal adoption now works from an operator CSV of postmeta `_wc_bitrix24_deal_id`, writing the map row before the Bitrix stamp so a failed stamp cannot leave an order unmapped (and duplicated after the flip).

## Commits
- c5d43a0 feat(12.1-04): EntityDeduper never persists or trusts SHADOW- contact/company ids
- f57a0b6 feat(12.1-04): adopt-legacy overwrites shadow rows, maps before stamping, accepts --legacy-map-csv

## Behaviour
- Contact/company: a SHADOW- id from contactAdd/companyAdd is returned but not stored (decision logged `shadow_not_persisted`). An existing SHADOW- row is ignored by lookups (no contactUpdate/companyUpdate on it) and overwritten with the real id (updateOrCreate for contacts, row update for companies). Deal lookup was already handled in 12.1-01.
- Adopt-legacy: real deal map row still skips (idempotent); SHADOW- row is overwritten and counted adopted. Legacy id source = `legacyDealIds[orderId]` (CSV) first, else Woo REST meta_data. Map row written first via updateOrCreate; `dealUpdate` stamp wrapped in try/catch for BitrixPermanentException (Log::warning "legacy UF stamp failed"); transient exceptions still propagate for chunk retry.
- `--legacy-map-csv=<file>`: requires `--adopt-legacy-deal-ids` (else exit 2 INVALID). Header must be exactly `order_id,deal_id`; both columns positive integers; order_id unique. Any violation lists line numbers, exits 1, creates no run and dispatches nothing. CSV order ids become the scope (no `--since` needed; `--only-order-id` narrows it). Banner prints the path and row count. Woo `orders/{id}` is still fetched per order (for status); missing meta_data does not block adoption.

## Operator procedure (run by the operator, never an agent)
1. Read-only export on the live Woo DB (prefix `wpb4_`, DB meetingstoreco_wp28). HPOS is on, but the plugin's meta is in postmeta keyed by order id:
   ```sql
   SELECT 'order_id' AS order_id, 'deal_id' AS deal_id
   UNION ALL
   SELECT post_id, meta_value FROM wpb4_postmeta
   WHERE meta_key = '_wc_bitrix24_deal_id' AND meta_value <> '';
   ```
   exported as CSV (e.g. `mysql ... --batch --raw` then convert tabs to commas, or `INTO OUTFILE`); first line must be `order_id,deal_id`. Check it also covers HPOS order ids: if some orders have no postmeta row, also check `wpb4_wc_orders_meta` with the same meta_key (same two columns, `order_id` column instead of `post_id`) and append.
2. Copy the CSV to the ops app host, then DRY RUN first (default mode is dry-run for other modes, but adopt-legacy writes map rows for real; the Bitrix stamp is shadowed while `CRM_WRITE_ENABLED=false`). Review the banner row count against the export:
   `php artisan bitrix:backfill-orders --adopt-legacy-deal-ids --legacy-map-csv=/path/legacy.csv`
   Validate the CSV alone first by temporarily pointing at a 1-2 row sample file.
3. Optional cap: `--only-order-id=185152,185264` narrows to listed orders.
4. VERIFY VIA BitrixEntityMap, not command output (it only dispatches; processed counts are not proof):
   `SELECT woo_id, bitrix_id, created_via FROM bitrix_entity_map WHERE entity_type='deal' AND created_via='adopted_legacy';` — row count must equal CSV row count, `bitrix_id` must match the CSV deal ids, and no `bitrix_id` may start with `SHADOW-`:
   `SELECT COUNT(*) FROM bitrix_entity_map WHERE bitrix_id LIKE 'SHADOW-%';` must be 0 (also contacts/companies).
5. After the flip (`CRM_WRITE_ENABLED=true`) the UF_CRM_WOO_ORDER_ID stamp is only real once writes are enabled; the map row alone is what PushOrderToBitrixJob consults, so cutover does not depend on the stamp. Re-running the same command after the flip is idempotent (real rows skip) and would apply the stamp only to unmapped orders.

## Deviations from Plan
None in scope. Observations:
- Company map rows use `woo_id = 0` under UNIQUE(entity_type, woo_id), so only one company row can exist; a second distinct company create would violate it. Pre-existing design, not changed here (prod has exactly 1 company row, consistent with this). Flag for 12.1-06/follow-up if company dedupe is expected to scale.
- A stale SHADOW- company row with a different dedup hash than the incoming company is not overwritten (only a hash match is); with the new no-persist rule no new such rows can appear.

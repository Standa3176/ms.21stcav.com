## Implementation Decisions

### Deal creation timing
- **D-01:** Create the Bitrix deal **only once the order is paid**: status `processing`, `on-hold` (PO / BACS), or `completed`. `pending`, `failed`, `cancelled`, `checkout-draft` never create a deal. An `order.updated` that first reaches a paid status creates the deal (today's D-10 race guard assumes `order.created` creates; that changes).
- **D-01a:** Exception (user decision 2026-10-27): YITH quote-request statuses `ywraq-new` and `ywraq-pending` **do** create a deal, in stage `NEW`, as the plugin does today — they are sales leads. Stage `NEW` with no product cost expected; Cost/Predicted Margin rules (D-05/D-06) still apply. The deal-creating status list is config-driven.
- **D-02:** Orders that never get paid produce no Bitrix writes at all (no contact/company upsert either), so abandoned checkouts stop creating CRM noise.

### Products on the deal
- **D-03:** After `crm.deal.add`, set product rows with the existing `BitrixClient::dealProductRowsSet()` (idempotent replace) using the same row shape as `PushQuoteToBitrixDealJob` (PRODUCT_NAME, PRICE inc VAT, PRICE_EXCLUSIVE/NETTO ex VAT, QUANTITY, TAX_RATE 20, TAX_INCLUDED Y, CUSTOMIZED Y, MEASURE pcs). Include a shipping row when shipping_total > 0 so the deal OPPORTUNITY reconciles with the order total.
- **D-04:** Re-set product rows on `order.updated` only when line items changed (payload hash), never on every status tick.

### Cost and Predicted Margin
- **D-05:** **Cost** = Σ (product `buy_price` ex VAT × quantity) over product lines, resolved by SKU at push time. **Predicted Margin** = product net sales ex VAT (line totals after discounts, ex tax) − Cost. Shipping excluded from both.
- **D-06:** If **any** line has no resolvable buy price, leave **both** fields blank (never write a partial cost that understates margin) and record a flag (integration event / suggestion) naming the order and SKU(s).
- **D-07:** The Bitrix `UF_CRM_*` codes for Cost and Predicted Margin must be discovered from `crm.deal.fields` by label, not guessed. ⚠️ Two different deal fields are both labelled "Actual Margin" — Actual Margin is NOT written by this phase (the dashboard reads `UF_CRM_1610623973323` as actual margin; do not touch it).

### Parity + configuration
- **D-08:** Seed `CrmPipelineSetting` / `CrmStatusMapping` / `CrmFieldMapping` to reproduce the plugin's deal (category, stage per status, `ASSIGNED_BY_ID`, `TYPE_ID`, `SOURCE_ID`, UTM, the plugin's `UF_CRM_*` fields) via a reviewable seeder/command, not ad-hoc admin clicks, so prod config is reproducible.
- **D-09:** Required deal fields in the target pipeline (seen in the plugin mapping screen: Cost, Predicted Margin marked required) must be satisfied or `crm.deal.add` is rejected — D-05/D-06 interplay: if D-06 blanks them and Bitrix requires them, the planner must surface that conflict, not paper over it with 0.

### Cutover
- **D-10:** Cutover order: adopt legacy deal ids first (`bitrix:backfill-orders --adopt-legacy-deal-ids`, reads postmeta `_wc_bitrix24_deal_id`), then create the Woo webhook (order.created + order.updated → `/webhooks/woo/order`), flip `CRM_WRITE_ENABLED=true`, then deactivate **only** `woocommerce-bitrix24-integration` with WP-CLI. Do **not** run `cutover:disable-legacy-plugins` — it also disables `stock-updater`.
- **D-11:** Shadow run first: webhook URL set + webhook live + `CRM_WRITE_ENABLED=false` for ≥ 3 days alongside the plugin; compare shadow payloads to the plugin's real deals for every order before flipping.
- **D-12:** Rollback = reactivate the plugin + `CRM_WRITE_ENABLED=false`; the gap between is covered by `bitrix:backfill-orders --only-order-id=…` (verify via `BitrixEntityMap`, not command output — it only dispatches).

### Post-planning decisions (user, 2026-10-27)
- **D-13:** Flip order **supersedes D-10's ordering**: deactivate the ITGalaxy plugin FIRST, then set `CRM_WRITE_ENABLED=true` immediately after. Orders in the gap get no deal; the post-flip check lists them and they are backfilled (`--only-order-id … --live`). No overlap window, no duplicate-deal cleanup.
- **D-14:** Keep the webhook source allowlist — order webhooks are processed only when `X-WC-Webhook-Source` is the live shop (`www.` normalised); clones/staging are dropped and logged.
- **D-15:** Keep the create-floor — orders at or below the last plugin-era order id never auto-create a deal from `order.updated`; misses there are manual backfills.
- **D-16:** Product-row `TAX_RATE` is derived per order line from the Woo line tax (20 / 0 etc.), **not** fixed at 20 (amends D-03). Shipping row likewise from shipping tax.

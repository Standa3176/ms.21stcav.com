# Three guards at the supplier-data trust boundary

All three came out of the 260904 Fable review of the auto-create → ingest → pricing →
publish domain. Each is a place where unvalidated supplier data reached customers, or
where verified data was destroyed.

## 1. A throttled price PUT left products LIVE WITH NO PRICE

`PublishProductJob` splits the create: POST without `regular_price` (Cost-of-Goods plugin
clobbers it otherwise), then a price-only PUT. Any failure on that second call was caught
and logged, on the stated grounds that it was *"self-healing — the sell_price reconciler
picks it up"*.

**That reconciler is gated off** — `config/cutover.php:129`,
`CUTOVER_SELL_PRICE_RECONCILE_ENABLED` defaults to false, and `routes/console.php:619-623`
only includes `sell_price` in the nightly `cutover:auto-sync` when it is true. So a
throttled price PUT left the product live with an empty price, silently, indefinitely.

The throttle fires **by design** during an approve-burst, which puts the tail of every
burst in exactly this state.

**Fix:** re-fire the price through `ProductPriceChanged`. `PushPriceChangeToWoo` is a
queued listener that already performs this exact write with throttle deferral, so the retry
inherits the machinery instead of reinventing it.

⚠️ **VAT trap avoided.** `$deferredPrice` is POST-strip, but `ProductPriceChanged`'s
contract is INC-VAT pennies — the listener applies the VAT decision itself via
`WooRegularPriceFormatter`. Handing it the stripped value would have stripped twice: a
silent 20% error on precisely the products a burst already mishandled. Hence
`$priceIncVatPennies`, captured in `buildCreatePayload` before the strip.

## 2. Re-drafting DESTROYED corrected barcodes

`GenerateProductDraftsCommand` builds `$contentValues` including `ean`, and the
already-exists branch does `$existing->forceFill($contentValues)->save()` under a comment
saying "Regenerate CONTENT only". `ean` is not content.

`43BDL5050D/00` was corrected to `8721038102253` on 2026-08-28, published, verified PASS —
and held the fabricated `43505000` again on 08-31 because a re-draft ran over it. Woo was
the only place the good value survived.

Two changes:

- **`ean` no longer rides the update `forceFill`.** It is only written when the existing
  value is EMPTY. A verified barcode can never be replaced by a feed-derived one.
- **The SKU fallback is checksum-gated.** `'ean' => normaliseEan($facts['ean']) ?? normaliseEan($sku)`
  *was* the SKU-digit-stripper: `normaliseEan()` only checks 8-14 digits, so
  `43BDL5050D/00` → `43505000` passed. Now routed through `firstValidGtin()`.

## 3. `WooGtinPublisher` PUT whatever string it was handed

The single choke point for Woo GTIN writes had no validation, and
`products:publish-sourced-eans` has none of its own. On 2026-08-28 it came within one SKU
of pushing `61U3010000AC`'s fabricated `613010000` live, purely because that SKU was still
in a `--skus` list.

Now refuses on checksum **or** padded-prefix and returns `'invalid'`. The command reports
it as `REFUSED — … is not a valid GTIN`, with its own counter, rather than letting it fall
into `skipped (no local EAN)` — which would describe a product that HAS one as though it
did not, and is how a fabricated barcode stays invisible.

**A refused value is left alone locally.** This is a publisher, not a cleaner; the value is
evidence of what the feed said and belongs to `products:identity-health-check`.

## New shared helpers — `NormalisesEan`

- `isPlaceholderGtin()` — `^\d{4,8}0{5,}\d$`. **Five** or more zeros then any final digit,
  not six: the check digit is only 0 by coincidence. The narrow `0{6,}$` form caught
  `4740100000000` and missed Vision's `4934292000003` (same shape, check digit 3).
- `firstValidGtin(...$candidates)` — first candidate that survives both gates, else null.
  Null is the right answer: an empty GTIN is a supported state for Google Shopping, a
  fabricated one is a disapproval.

`isValidGtinChecksum()` already existed, documented in-repo as *"the MISSING gate"*, and
until now **only read paths called it**.

## Deliberately NOT changed

**`exclude_from_auto_update` does not protect `buy_price` from `supplier:db-sync`.** The
carve-out helper is applied only to the obsolete-demote and stale-cost paths, while
`SupplierDbSyncCommand:364-367` updates cost and stock for every matched product. The
sync's own doc comment says the flag marks products it "must never mutate automatically",
so the semantics are inconsistent — but changing it would alter cost behaviour for every
excluded product, and that is an operator decision, not a bug fix.

## Tests

- `NormalisesEanTest` — placeholder detection incl. the non-zero check digit; real barcodes
  and 12-digit UPC-A must not be swept up; `firstValidGtin` returns null rather than a
  SKU-derived number.
- `WooGtinPublisherTest` — refuses bad checksum; refuses a padded prefix that checksums;
  leaves the local ean intact when refusing; still publishes genuine GTIN-13 and UPC-12.
- `PublishSourcedEansCommandTest` — refuses a fabricated barcode, nothing reaches Woo, the
  local value survives. Existing fixtures moved from `EAN-P1`-style placeholders to real
  GTINs, since the gate now (correctly) rejects non-numeric strings.

**Not covered by a test:** the `ean`-preservation branch in `GenerateProductDraftsCommand`.
That command talks to the supplier MySQL through `mysqli` directly, with no seam to stub,
so there is no cheap way to exercise it. The gate it depends on (`firstValidGtin`) is
unit-tested; the preservation itself is not.

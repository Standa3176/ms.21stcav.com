# Suggestions opens on what Auto-create can actually act on

Items 1 and 5 from the Fable 5.1 UI/UX review of the admin menu.

## Problem

### 1. The list opened on rows the bulk action silently discards

`SuggestionResource` defaulted `kind` to `new_product_opportunity` and `status` to
`pending`, but left `on_supplier_db` unset. That opened the screen on ~8,000 pending rows
of which roughly 96% are competitor-only SKUs **no supplier carries**.

The bulk "Auto-create selected" action filters those out — silently. So selecting a
screenful and dispatching produced nothing at all. An operator spent two days
(2026-08-30/31) believing the button was broken. It was not; the default was.

The screen carried three different definitions of "actionable":

| Surface | Predicate |
|---|---|
| the list | everything pending |
| the sidebar badge | pending + sourceable + **≥ 3 competitors** |
| the bulk action | pending + sourceable |

Clicking the badge landed on a list that did not show the set the badge had counted.

### 2. The Readiness badge described work that does not exist

A sourceable row with a blank or junk brand rendered as amber **"Needs brand"**, tooltip
*"parks until a brand is set"*.

That brand is `evidence.brand` — scraped from the **competitor** listing. The pipeline
never reads it. `products:draft-from-suggestions` resolves the brand from
`supplier_products.manufacturer`, and with `--create-missing-brands` (which the Mon/Thu
cron always passes) creates the Woo term itself. It parks only on `no_manufacturer` —
i.e. when the *supplier* row has no manufacturer, which this badge does not measure.

Amber + "needs" was telling operators to do work that does not exist, on a row that would
have created fine.

## Changes

**Alignment (item 1)**

- `Suggestion::scopeSourceablePending()` — new single source of truth for
  pending + `new_product_opportunity` + SKU in `supplier_sku_cache`.
  `scopeHighConfidenceSourceable()` now composes onto it and only adds the ≥ 3 gate, so
  the two predicates cannot drift.
- `on_supplier_db` filter `->default('yes')` — the list opens on the sourceable set.
- `getNavigationBadge()` counts `sourceablePending()`, the same set. The tooltip still
  shows all three tiers (`N high-confidence • N sourceable • N raw`); the Home dashboard
  tile keeps the narrower scope because it is labelled "high-confidence".
- `getNavigationBadgeTooltip()`'s `$sourceable` line was an inline `whereRaw` duplicate of
  the predicate — now the scope.
- `->persistFiltersInSession()` so widening past the default survives navigation.
- `->indicateUsing()` chip on the filter, because this is a default the operator did not
  choose — and because it explains the one baffling case: Readiness = "Not sourceable"
  with `on_supplier_db` still `yes` asks for rows that are both in and not in the feed.
- Empty-state text rewritten to say what the list is filtered to and how to widen it.

**Honesty (item 5)**

- `readinessFrom()` returns **`Brand unlisted` / `info`** instead of `Needs brand` /
  `warning`. Filter option relabelled; the filter **value** stays `needs_brand` so
  bookmarked filter URLs keep working.
- Tooltip now states what the pipeline does: takes the brand from the supplier feed,
  creates the Woo term if new, and parks only if the supplier row has no manufacturer.

## Two bugs the default exposed

Both were latent — nothing applied `on_supplier_db` unless an operator picked it by hand.

1. **`no such function: JSON_UNQUOTE` on SQLite.** The filter built its EXISTS clause from
   a hardcoded MySQL JSON string instead of the driver-portable
   `self::sourceableExistsSql()` the readiness filter already used. Prod (MariaDB) was
   fine; every test that rendered the list now blew up. Fixed to use the helper.
   (The SQLite ↔ MariaDB trap, again.)

2. **The filter deleted rows it has no opinion about.** "On supplier DB" is a
   `new_product_opportunity` concept. A `margin_change` or `crm_push_failed` row is not
   "unsourceable" — the question does not apply. An operator clearing the Kind filter to
   look at those kinds would have got a near-empty list and no clue why. The `'yes'`
   branch is now guarded to `kind != new_product_opportunity OR EXISTS(...)`. The `'no'`
   branch stays strict: that one is an explicit request for competitor-only opportunities.

## Verification

`tests/Feature/Suggestions/SuggestionsDefaultFilterTest.php` (new, 6 cases) pins:

- the list opens on sourceable rows only; the competitor-only orphan is hidden
- clearing the filter still reaches it
- the badge reads `2` — not `1` (high-confidence) and not `3` (raw pending)
- the tooltip still exposes all three tiers
- the ≥ 3 competitor gate survived the scope refactor
- a `margin_change` row is not hidden by the default

Six existing tests needed fixture updates, in two kinds:

- NPO fixtures seeded into `supplier_sku_cache` (a realistic opportunity is sourceable) —
  `NewProductOpportunityApproveActionTest`, `SuggestionResourceAutoCreateKindsTest`
- filters cleared to test another filter in isolation — `SuggestionBrandFilterTest`,
  `SuggestionReadinessFilterTest` (the `not_sourceable` case now contradicts the default)

`RejectWithAgentFeedbackActionTest` needed **no** change once the kind-guard was added —
which is what made that guard worth having rather than a test convenience.

## Not changed

No pipeline behaviour. No pricing, taxonomy, rules, or overrides. The bulk action's own
sourceability filter is untouched — the point was to make the list agree with it, not to
loosen it.

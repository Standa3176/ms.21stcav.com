# Persist the resolved price locally, not just to Woo

## Problem

260904-r1h made `PublishProductJob` resolve the pricing rule for the **Woo payload**. It did
not write that price back to `products.sell_price`, so the two diverge from the moment of
publish.

Observed live on 2026-09-05, running the Monday cron early with `--limit=3`:

| SKU | Woo (customers see) | `products.sell_price` |
|---|---|---|
| `48077` | 1.90 | 1.85 |
| `71277` | 5.90 | 5.96 |
| `36701` | 1.70 | 1.73 |

## Why it matters

`pricing:health-check` reads `products.sell_price`, **not Woo**. So a product correctly live
at £34.25 could be reported as a 319% suspect cost because the local row still said £126.54 —
a false alarm, on precisely the products that check exists for.

Same class as the EAN work: local and Woo drift independently, and a local PASS is not a
storefront PASS.

Severity is bounded — the 07:00 `pricing:undercut-competitors --live` run rewrites the local
value and pushes it, so the window is hours rather than permanent. But the check is least
trustworthy in exactly that window, which is when a newly published product most needs it.

## Fix

`handle()` already back-fills `woo_product_id` and Woo's reconciled slug after the create.
`sell_price` now joins that same `forceFill`, using `$priceIncVatPennies` — the inc-VAT value
`buildCreatePayload` captured before any ex-VAT stripping.

Written in `handle()`, not in `buildCreatePayload`: a payload builder should compute, not
persist.

Only written when it actually differs, so a manual row or an unresolvable rule is a no-op.

## Tests

- a draft carrying £126.54 RRP on a £25.16 cost ends with `sell_price = 36.83` locally,
  matching what was pushed
- a `manual` row keeps its £99.00 untouched

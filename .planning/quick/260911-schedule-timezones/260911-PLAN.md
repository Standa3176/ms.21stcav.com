# Four scheduled commands were running on UTC, not UK time

Operator asked whether all project timezones are UK.

## What was found

`config('app.timezone')` is **UTC** — correct, and it stays. Timestamps are
stored in UTC and reinterpreting that would be a far larger, riskier change
than anything it fixes.

But a `Schedule::command()` without an explicit `->timezone()` inherits it. So
`dailyAt('03:00')` means 03:00 **UTC** — which is 04:00 London for the seven
months of BST.

**47 of 51 entries set `Europe/London`. Four did not:**

| command | slot | actual, in BST |
|---|---|---|
| `activitylog:prune --days=365` | 03:00 | 04:00 London |
| `integration-events:prune --days=90` | 03:10 | 04:10 London |
| `sync-diffs:prune` | 03:30 | 04:30 London |
| `products:reconcile-woo-maintenance` | 04:30 | 05:30 London |

## Why it mattered

`routes/console.php` staggers work in deliberate ten-minute slots — 03:00,
03:10, 03:20, 03:25, 03:30, 03:40, 03:50, 04:00. Four entries sliding an hour
out of position every summer collapses the gaps that stagger exists to create.

Three of the four are prunes, where an hour's drift is harmless. The fourth is
not: **`products:reconcile-woo-maintenance` writes to Woo**, and in BST it
drifts toward the Mon/Thu 05:00 auto-create publish, where both compete for
the same 60/min write throttle — the throttle that has now caused two separate
incidents on this codebase.

## Fix

`->timezone('Europe/London')` on all four, matching the other 47, plus a note
in the file explaining why every entry needs it.

`tests/Architecture/ScheduleTimezoneTest.php` reads the RESOLVED schedule
rather than grepping the file, so an entry added from any service provider is
caught too. It treats both shapes as failures — a null timezone and an
explicit non-London one — because Laravel's default depends on version.

A second case pins `app.timezone` as UTC, so nobody later "fixes" schedule
drift by flipping the global and reinterpreting every stored timestamp.

## Not changed

Display timezone. Filament renders timestamps in the app timezone, so admin
screens show UTC — an hour off local during BST. That is a presentation
concern with a different fix (per-column `->timezone()` or a Filament-wide
display default) and a different risk profile; it is not a scheduling bug and
was out of scope for this check.

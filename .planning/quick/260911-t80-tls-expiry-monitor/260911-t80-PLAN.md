# Nothing was watching certificate expiry

## The incident

`meetingstore.co.uk`'s TLS certificate expired at **09:34 UTC on 2026-09-11**.
It was discovered at roughly 16:30 — seven hours later — when a catalogue-wide
`trade:sync --live` returned:

```
LIVE complete — 3322 at target, 322 capped by retail, 689 suppressed,
0 unchanged, 4333 failed. 0 written to Woo.
    write failed for 1812250 — cURL Error: SSL certificate problem:
    certificate has expired
```

For those seven hours every visitor to the shop met a browser security warning,
and every Woo write from this app failed.

## Root cause: two certificate systems, one renewal

```
certbot certificates
  api.21stcenturyav.info   VALID: 62 days
  ms.21stcav.com           VALID: 38 days
  staging.meetingstore...  EXPIRED (since 2026-05-01)
```

**`meetingstore.co.uk` is not in that list at all.** nginx serves
`/etc/pki/tls/certs/meetingstore.co.uk.bundle` — CWP's AutoSSL store, not
certbot's `/etc/letsencrypt/live/`.

certbot renews its own domains on a healthy systemd timer
(`certbot-renew.timer`, last run 12h before the incident). CWP AutoSSL had
**no renewal scheduled anywhere** — not root's crontab, not `/etc/crontab`,
not `/etc/cron.d`, not `cron.daily`. CWP ships
`cron_autossl_renew_all_domains.php` for exactly this and nobody ever
scheduled it. It is ionCube-encoded, so its CLI contract could not be read;
renewal went through the CWP panel.

`staging.meetingstore.co.uk` had been expired since **1 May** — four months,
unreported. That is the real measure of the gap: this was never going to be
caught by anything.

## What was built

**`tls:check-expiry`**, scheduled daily at 08:20 London — deliberately BEFORE
the 09:30 pricing health check, because when TLS is down every Woo write fails
and this says why first.

Reports expired, expiring inside the window (default 14 days), and unreachable
hosts. Exit code is the durable signal and the email a courtesy, matching
`pricing:health-check`: a missing subscriber must never make a real expiry
look like a pass, and there is a test for precisely that.

**It asks the socket what is being SERVED**, rather than reading either tool's
state. That is the design point — it stays true if a domain moves between
certbot and CWP, and it catches the failure mode neither tool reports: a
renewal that succeeded on disk but whose web server was never reloaded.

14 days was chosen because it sits inside Let's Encrypt's 30-day renewal
window, so a warning always means "renewable right now", never "come back
later", and it spans two weekends.

**Plus a circuit breaker on `trade:sync`.** It ground through all 4,333
products retrying a failure that could never succeed. It now aborts after 15
consecutive write failures and says the cause is environmental. An hour of
wasted wall-clock becomes about ten seconds.

## Verification

10 cases for the command, including the real shapes: an expired cert, one 13
days out, an unreachable host, and the no-subscriber case. The inspector is
behind a `TlsInspector` contract so tests substitute the network — a test that
opened real sockets would pass or fail on somebody else's infrastructure and
would go green the day the thing it catches gets fixed.

210 tests across TradePricing + Alerting + Architecture. Deptrac 0 violations.

## Still open — infrastructure, not code

- **Schedule CWP's AutoSSL renewal.** The check tells you it is about to
  happen; it does not renew anything. Either get
  `cron_autossl_renew_all_domains.php` scheduled (its argument contract is
  unknown — ionCube), enable auto-renew in the CWP panel, or move the domain
  to certbot, which demonstrably works on this box.
- `staging.meetingstore.co.uk` — renew or remove the vhost; it will fail this
  check daily until one or the other.
- `TLS_CHECK_HOSTS` defaults to the storefront and the ops app. Add
  `api.21stcenturyav.info` and `rams.21stcav.com` if they matter.

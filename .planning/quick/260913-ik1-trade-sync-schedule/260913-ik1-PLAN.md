# 260913-ik1 — Schedule trade:sync after the daily repricing

**Branch:** `quick/260913-trade-sync-schedule`
**Trigger:** operator found SKU `47132` live with a standard price and no trade price.

## The problem

`trade:sync` had **never been scheduled**. It was run once by hand on
2026-09-11 and never again, which produced two faults that both grew daily:

1. **New products got no trade price at all.** `47132` (LINDY Cat6A cable) was
   created 2026-09-13 11:38 and read back from the Woo REST API with *no
   b2bking meta of any kind* — not an empty value, no key. Every product
   auto-created since the manual run was in the same state.
2. **Existing trade prices were computed against pre-repricing retail.** Trade
   price is a discount off `products.sell_price`; the 08:00 undercut moved
   **2,205** retail prices on 2026-09-13 alone. Every trade price on the
   storefront was a day behind, and invisibly so — the numbers still look
   plausible, they are simply derived from the wrong input.

A 20-product sample confirmed the catalogue was otherwise healthy (19 of 20
carried a trade price), so this was a *decay* problem, not a broken sync.

## What was built

`routes/console.php` — `trade:sync --live --changed-only`, daily 08:30
Europe/London, `withoutOverlapping(180)`, `onOneServer()`, gated on
`config('b2b.storefront.sync_schedule_enabled')` (default **true**, env
`B2B_TRADE_SYNC_SCHEDULE_ENABLED` is an off switch needing no deploy).

**Why 08:30.** Trade price derives FROM retail. Running before the undercut
publishes trade prices computed from yesterday's retail. The undercut writes
`sell_price` synchronously so the database is correct the moment it returns;
30 minutes also lets its ~20-minute 60/min Woo push queue drain, so trade
writes are not queued behind retail writes competing for the same throttle.

**Why `--changed-only`.** Without it all ~4,333 published products are written
nightly — 72 minutes of write budget at the 60/min throttle, for a value that
moves on a few hundred. `--changed-only` spends a GET per product instead
(reads are not throttled) and writes only real differences. Writes are the
scarce resource, not reads.

**Why `config()` not `env()`.** `env()` returns the default under
`config:cache`, which is exactly how the first post-cutover 08:00 undercut
silently never fired.

## The test, and the bug in the first version of it

`tests/Architecture/TradeSyncScheduleTest.php` pins that the entry exists, runs
**after** the undercut, carries `--live --changed-only`, and sets
`withoutOverlapping`. `ScheduleTimezoneTest` already covers Europe/London.

The first version of the ordering test **passed while the ordering was wrong.**
`pricing.undercut_schedule_enabled` defaults to FALSE in the repo (opt-in via
env, true only on prod), so the undercut is never registered under test and the
assertion took an early-return branch that skipped whenever it could not find
the undercut — i.e. always.

Caught by mutation: moving `trade:sync` to 07:30, *before* the undercut, and
watching it still report 4 passed. The fix forces both flags on and
re-registers `routes/console.php` onto a fresh `Schedule`. That needs
`ScheduleFacade::clearResolvedInstance()` — the facade caches its resolved
instance, so rebinding the container alone leaves `Schedule::command()` writing
to the old object and the fresh Schedule comes back empty.

Re-verified by mutation after the fix: 07:30 fails, 08:30 passes.

## Not done, deliberately

**The B2BKing "Trade" group (167509) hazard is recorded in `config/b2b.php`,
not coded around.** That group has no users but carries a dynamic rule
`Trade Price = Cost + 8%` reading WOO's own cost field — which was populated
once at the 2026-05-23 bulk load and never maintained. 6 of 25 sampled
published products (24%) have no Woo cost, every one created after that date.
If a customer is ever moved into 167509, those price at £0 + 8% = **£0**,
including `IDS-UVC-P38` at £1,066 cost. The right fix is deleting the rule in
B2BKing admin — an operator action. Building a code guard against a rule that
should not exist would entrench it.

## Deploy note

Requires no env change — the flag defaults true. After `deploy.sh`, confirm
with `php artisan schedule:list | grep trade:sync` (prints UTC; 08:30 London is
07:30 UTC outside BST, 07:30 UTC during BST reads as 08:30 London).

# 260927-p41 — the ad shortlist: fix the margin, model the demand

**Branch:** `quick/260927-ad-margin-vat-basis`
**Trigger:** *"ms has not been live for a year but i want to relaunch ie there is
no sales numbers for you to use. can you review the sku list and estimate weekly
uk web sales from the web to get to a list of ads skus (at least 50!)"*

Two problems stood between that request and a usable list. The first had to be
fixed before any list could be trusted at all.

---

## 1. Every margin in the ad tooling counted VAT as profit

`products.sell_price` is **VAT-inclusive** — `PriceCalculator::compute()` returns
a gross retail price. `products.buy_price` is the supplier's **ex-VAT** cost.
Three surfaces subtracted one from the other:

| Surface | Expression |
|---|---|
| `ShoppingCandidateScanner` | `$sellPence - $buyPence` |
| `AdCandidateScanner` | `$sellPence - $buyPence` |
| `ReadMarginOpportunityTool` | `ORDER BY (sell_price - buy_price) DESC`, plus a `sell_price > buy_price` filter |

Every reported margin was therefore overstated by `sell / 6` — **16.67% of the
sell price**, money that belongs to HMRC:

| sell (inc) | buy (net) | reported | true cash | phantom |
|---|---|---|---|---|
| £1,200 | £980 | £220.00 | £20.00 | £200.00 |
| £5,000 | £4,200 | £800.00 | **-£33.33** | £833.33 |
| £9,000 | £7,600 | £1,400.00 | **-£100.00** | £1,500.00 |

(Illustrative price pairs chosen to show the arithmetic — not measured rows.)

Two consequences, both fatal to the request:

- **`sell/6` alone clears the £199 default floor at any sell price above £1,194.**
  Across the expensive half of an AV catalogue the margin gate was filtering on
  *price*, not profit.
- A product sold at a **real loss** could rank as an £800 winner. Ad spend against
  that list buys units we lose money on.

Fixed by stripping VAT off the sell before subtracting, via
`PriceCalculator::stripVat()`, so the rate and the rounding mode stay in the one
class that already owns them. Rows now also carry `net_sell_price_pence` and
`margin_pence_gross_basis` (what the old figure would have said) so an older
export reconciles rather than silently contradicts.

### The existing tests did not catch this, and nearly did not catch the fix

Re-basing the gate/ranking fixtures made their numbers correct, but reverting the
fix still left **21 of 26 green**: those tests only assert that an eligible row
stays eligible, and a gross-basis margin is always *larger*. Only exact-value
assertions moved.

So `tests/Feature/Pricing/AdMarginVatBasisTest.php` pins the case that
distinguishes the two formulas by **verdict**: a product at £5,000 inc VAT against
a £4,200 ex-VAT cost, which is +£800 on the old basis and -£33.33 on the true one.
It must be excluded, and the funnel must name the *margin* gate as the reason.

### Fixture basis

Every price the scanner fixtures pass is now stated **net**, and the seed helpers
add VAT on the way in. This is what those fixtures always meant — the comments
said "sell £350 / buy £100 -> margin £250", and £250 is the true margin only on a
net basis. Scaling both sides preserves every net-vs-net relation, so
`beat_pct_bps` (a ratio) is unchanged and each matrix row keeps its verdict.

---

## 2. There is no demand signal, so demand had to be modelled

The shop has taken no orders for about a year. `last_sales_count_90d` is a year
stale at best and zero at worst; GA4 has nothing to say about a dark site. The
input an ad ranking normally uses does not exist.

The previous ranking was `competitor_count x margin_pence`. With cash margin
rising with price and web demand falling with it, that ranks a £9,000 LED wall
above a £400 video bar — and says nothing about whether a product is web-bought
at all.

`WebDemandEstimator` estimates weekly UK web units. The split matters more than
the formula:

| | Signal | Source |
|---|---|---|
| **MEASURED** | breadth | distinct tracked resellers currently listing the SKU |
| **MEASURED** | persistence | distinct days it appeared in feeds over 12 weeks |
| **MEASURED** | price | our own net sell price |
| **ASSUMED** | class base rate | units/week nationally for this KIND of product |
| **ASSUMED** | price-band decay | how self-serve demand falls as price rises |
| **ASSUMED** | breadth / persistence weights | |

`units = class_base x price_factor x breadth_factor x persistence_factor`

Every assumed number lives in `config/ad_demand.php` with its reasoning, because
the class base rates are the dominant error term and an AV trader knows them
better than this codebase does. Retune and re-run; the shortlist re-ranks.

New sort `--sort=profit` (now the default) ranks on **estimated weekly units x
true cash margin** — what an ad budget is actually competing for. The CSV exports
every factor per row so a single estimate can be argued with rather than taken on
faith, and the command prints a **band** ("2-5/wk") beside the number because the
model cannot justify decimal precision.

`daysSeenByKey()` uses `COUNT(DISTINCT DATE(recorded_at))`, not `YEARWEEK()` —
`DATE()` exists on both MySQL and SQLite, and the suite runs SQLite while
production is MySQL. A MySQL-only function there would pass every local gate and
fail on the only machine that matters.

### What the tests pin

Direction and shape, never a magic output number — asserting "a 3-competitor £400
webcam is 14.6 units/week" would pin one guess in place and break the moment
someone tunes the config, which is what the config is for. So: demand falls as
price rises; rises with breadth; rises with persistence; persistence never reaches
zero and never exceeds 1.0; an unclassifiable title lands mid-table rather than at
either extreme; and a retuned config changes the answer without a code change.

Two real bugs came out of writing them:

- **"Shure MXA910 Ceiling Array Microphone" classed as a `speakerphone`**, because
  `microphone` was tested before the installed-AV keywords — putting a £150
  USB-device demand rate on a £3k specified ceiling array. `installed_av` now
  precedes the device classes.
- My own persistence assertion was wrong: one sighting in 84 days sits slightly
  *above* the floor, not on it. The code was right.

## 3. The finding that actually answers the question

The model against representative products with plausible margins, ranked by
expected weekly profit:

| product | units/wk | true margin | profit/wk | passes £199 floor? |
|---|---|---|---|---|
| Jabra Evolve2 65 Headset | 42.75 | £18.00 | £769.50 | **NO — excluded** |
| Jabra Speak2 75 Speakerphone | 18.00 | £35.00 | £630.00 | **NO — excluded** |
| Logitech Rally Bar Mini | 2.30 | £220.00 | £506.00 | yes |
| Logitech C920 Webcam | 49.50 | £9.00 | £445.50 | **NO — excluded** |
| Poly Studio X50 | 1.51 | £280.00 | £422.80 | yes |
| Samsung QB65C Signage | 1.30 | £90.00 | £117.00 | **NO — excluded** |
| Shure MXA910 Ceiling Mic | 0.06 | £450.00 | £27.00 | yes |

**The £199 margin floor excludes the three highest-profit candidates and keeps the
single worst one.** It is anti-correlated with what a relaunch wants: high cash
margin per unit in this catalogue means expensive specified kit, and expensive
specified kit is not bought from a web basket.

Order-of-magnitude, from my priors and plausible margins — not measured. But the
*direction* does not depend on the magnitudes: it follows from cash margin rising
with price while web demand falls with it, which is a property of the market, not
of this table.

So the shortlist should run with a margin floor near the ad-viability threshold
(`--min-margin-pence=4000`, about £40, which still covers a £30-100 Shopping CPA)
rather than the £199 default. That is the run that can reach 50+ rows with volume
behind them.

## NOT done — the list itself

Producing the 50 SKUs needs one read of the production catalogue (`products` +
`competitor_prices`), and prod reads were refused in this session. The command is
ready:

    php artisan products:shopping-candidates \
      --sort=profit --min-margin-pence=4000 --limit=200 \
      --csv=storage/app/research/ad-shortlist.csv

Also outstanding: GTIN coverage caps the list, because Google Merchant requires
one. The funnel's `missing GTIN` line quantifies it, and `--allow-missing-gtin`
shows what an EAN backfill would unlock.

The one input that would turn the estimate into a measurement is Google Keyword
Planner search volume (free, UK location) run against the exported sku/name
column.

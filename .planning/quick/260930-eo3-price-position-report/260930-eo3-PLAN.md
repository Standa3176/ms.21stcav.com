# 260930-eo3 — price-position report (PDF)

**Branch:** `quick/260930-price-position-report`
**Trigger:** a 50-part-number "RUN ADDS ON THESE PRODUCTS" list, with the ask:
*"output a pdf that marks the ones we are best priced currently, could be best
priced, and sold below cost/floor."*

## Why this is a command and not an answer

The verdicts need our live sell price, our supplier cost and the current
competitor feed. All three are in production, and this session has no SSH
credentials for that box (`~/.ssh` holds no private key, no agent is running,
and both `root@` and `stcav@` on port 2250 return `Permission denied`). So the
deliverable is the thing that produces the PDF **on the server**, run in one
line, with nothing to send back.

## The three verdicts, and three more the data forces

The ask names three states. Running real data through them surfaces three more
that would otherwise be silently folded into the wrong bucket:

| Verdict | Meaning |
|---|---|
| **Best price now** | our VAT-inc price is under the cheapest tracked reseller |
| **Could be best** | not cheapest, but undercutting the leader by 1p still clears the floor |
| **Cannot win at floor** | the leader sells below where our floor lets us go |
| **Below margin floor** | our live price is under cost + the floor markup, but still profitable |
| **BELOW COST** | net sell price is under the supplier cost — a loss on every unit |
| **No competitor data** | nobody tracked lists it |
| **No cost on file** | the floor cannot be computed |
| **Not in catalogue** | the part number resolves to no product of ours |

Three of these exist because collapsing them would mislead:

- **"Cannot win" is not "could be best."** Reporting a SKU as winnable that the
  pricing job will then refuse to move is the most expensive kind of wrong,
  because ad budget follows the report.
- **"Below floor" is not "below cost."** One is a policy breach that still makes
  money; the other loses money on every unit. Same colour, different action.
- **"No competitor data" is not "best price."** Absence of evidence. Calling it a
  win is a lie the whole report would rest on.

And a row can be **both cheapest and loss-making** — in fact that is usually
*why* it is cheapest. The loss takes precedence in the verdict, and the
competitive position is still printed beside it rather than discarded.

## The floor is borrowed, never re-derived

`PricePositionClassifier` delegates to `CompetitorUndercutPricer::decide()` — the
class that actually sets prices every morning — and reads the floor from the
same `PriceCalculator`. If the report computed its own floor the two would
drift, and the report would start recommending prices the pricing job rejects.

Worth stating because it is easy to get backwards: the floor margin is a
**markup on cost**, not a share of the sell price. `min_margin_floor_bps` of 600
means cost + 6%, which is about 5.7% *of* the sell price. A test pins the exact
figure (£100 net cost → £127.20 inc) so the two readings cannot be confused
later.

## VAT

`sell_price` is VAT-inclusive and `buy_price` is the supplier's ex-VAT cost
(260927-p41). So the competitive comparison is gross-vs-gross and the cost
comparison is net-vs-net. The PDF prints both bases and labels them, because
"sell minus cost" across the two — the bug fixed three days ago — is exactly how
a loss-maker comes to look like a winner.

## Matching

The input carries MANUFACTURER part numbers; `products.sku` is ours. Each row is
resolved in passes — exact SKU, then a normalised key (case-folded, everything
non-alphanumeric stripped, so `MVC S40-C5U-000`, `MVCS40-C5U-000` and
`mvc-s40-c5u-000` are one product) — and the pass that matched is printed.

A row matching nothing is reported as **Not in catalogue**, and if competitors
list it the PDF says so. "They stock it and we do not" is a sourcing action, not
a pricing verdict, and must not be scored as one.

## DOMPDF, not the Pdf facade

`QuotePdfRenderer` uses spatie/laravel-pdf, whose driver defaults to
`browsershot` — Node, Puppeteer and a headless Chrome. This command has to run
from an SSH session on the VPS, so it drives DOMPDF (pure PHP, already a
dependency) directly and cannot be broken by a missing Node install or a
`LARAVEL_PDF_DRIVER` pointing at Chrome. The cost is that the Blade template
must stay to simple table CSS; it does, and the verdict colours use a left
border as well as a tinted pill so the report survives greyscale printing.

## Two notes on the supplied list

- **50 rows, and two share a part number.** "Lenovo ThinkSmart PC Gen 2 - Teams"
  and "Lenovo ThinkSmart Core Gen 2 - NUC PC" are both `12X2S0000F`. One is
  wrong at source. The file keeps both and a test pins the duplicate, because
  de-duplicating would hide a data-entry error worth seeing.
- The list ships in the repo (`resources/reports/run-adds-part-numbers.tsv`) so
  the command runs with no setup.

## Run it

    php artisan products:price-position-report \
      --pdf=storage/app/research/run-adds-price-position.pdf \
      --csv=storage/app/research/run-adds-price-position.csv

The console prints the same table and a per-verdict summary, so the counts are
visible without opening the PDF.
